# 多 Agent 设计说明

## 为什么不是所有任务都使用多 Agent

少量门店的周复盘通常不需要角色交接。系统先计算品牌数、门店数、“门店 × 平台”单元数和数据阻断情况，再选择轻量或深度模式。这样可以证明 Agent 数量来自任务复杂度，而不是为了包装概念。

## 职责分离解决什么问题

| 风险 | 设计应对 |
|---|---|
| 同一个模型既分析又证明自己正确 | 行动审核 Agent 独立退回或否决 |
| 多品牌、多门店和三平台上下文混淆 | 质检全量数据，诊断按品牌—门店切片 |
| 数据问题被后续建议掩盖 | 数据阻断时跳过诊断、策略和审核阶段 |
| 建议没有证据或无法验证 | 交接强制携带来源行、证据、适用条件和验证指标 |
| 总控变成无边界的超级 Agent | 总控只能路由、排序和汇总，不能修改专业结论 |
| Agent 反复互相退回 | 策略自动修正最多一次，然后交给用户 |

## AI 与确定性程序的分工

- 确定性程序：数据校验、指标计算、周期比较、规则阈值、动作目录、安全词和任务状态。
- AI Agent：理解用户目标、解释事实、区分假设、适配策略、处理退回意见和生成用户报告。

这使关键数字和安全边界可以重复测试，同时保留 AI 对复杂经营语境的理解能力。

## 两种运行形态

WorkBuddy 安装包使用官方专家团结构，由一个主理人调度四个成员 Agent。本地编排器复用同一职责和交接协议，但只运行确定性业务内核，用于测试路由、阻断、审核和输出，不声称产生了五次独立模型调用。

## 可验证的演示场景

1. 单品牌、单门店数据自动进入轻量模式。
2. 多品牌虚构数据自动进入多 Agent 深度模式。
3. 重复粒度等阻断问题使后三个专业阶段停止。
4. 越权动作被安全拒绝，不进入任务列表。
5. 丢失来源命中的策略被退回，并触发最多一次修正标记。

## 面试中的准确表述

可以说“设计并实现了自适应的多 Agent 外卖经营诊断工作流，在 WorkBuddy 中使用原生专家团完成主理人与成员调度，并用本地确定性编排器验证路由、交接、证据门禁和审核逻辑”。

不应声称平台接口已接通、动作会自动执行、并行度已经得到平台保证，或多 Agent 已提升某个未经测量的准确率百分比。
